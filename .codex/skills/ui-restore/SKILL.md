# ui-restore

## 概述

用于把用户提供的 `HTML` 页面与同一页面的一个或多个设计图状态，落地为 `template/uniapp` 下可运行的 UniApp 页面。

围绕"页面还原"执行固定流程：解析输入路径、分析 HTML 结构、合并多状态交互、创建页面文件、补充路由、检查语法、连续三轮 UI 对比修正，以 **95% 还原度** 作为交付目标。

默认视觉基线为**块状圆角卡片风格**：页面外层优先使用浅灰底，核心信息区/表单区/提示区/弹层区优先使用白色圆角块承载，并补充柔和阴影形成层次。若设计图本身未遵循该风格，但用户或项目规范明确要求统一为块状圆角风格，则以规范为准对设计稿进行统一化调整，而不是机械照搬原稿。

## 适用场景

在以下场景触发此技能：

- 用户提供一个或多个 `HTML` 文件路径，并要求还原为 UniApp 页面。
- 用户提供一个或多个同一页面的设计图/截图，要求按图片效果还原页面。
- 用户明确给出 `uniapp` 页面目标路径，要求直接创建页面文件。
- 用户要求在还原页面时，同时创建或补齐 `pages.json` 路由配置。
- 用户说明同一页面存在多个 UI 状态，需要在一个页面内完成切换、交互或条件展示。

## 必要输入

优先从用户消息、当前附件和工作区内容中自行收集以下信息：

- `HTML` 路径：用户每次会提供。
- UniApp 页面路径：用户每次会提供，通常位于 `template/uniapp/pages/...`。
- 设计图或截图：可能是一张，也可能是多张；默认都属于同一个页面的不同状态。

在信息缺失时，优先做如下推断，而不是立刻中断：

1. 先从会话附件、打开文件、最近文件中寻找设计图与目标页面上下文。
2. 从 `HTML` 中提取页面结构、文案、图片位、状态块和交互区域。
3. 从设计图中识别视觉差异，整理为"默认态 / 空态 / 激活态 / 弹层态 / 加载态"等同页状态。
4. 仅在无法判断目标页面路径、HTML 路径或设计图归属时再向用户补问。

## 固定工作流

### 第 1 步：确认目标与边界

执行以下动作：

1. 读取用户提供的 `HTML` 文件。
2. 确认 UniApp 目标页面路径，例如 `template/uniapp/pages/activity/detail/index.vue`。
3. 识别所有设计图是否属于同一个页面；如果属于同页不同状态，禁止拆成多个页面实现。
4. 明确页面需要兼容 `H5` 与 `微信小程序`，优先使用 `uni.*` 能力，避免浏览器专属 API。

### 第 2 步：拆解 HTML 与设计图

执行以下动作：

1. 从 `HTML` 中提取页面骨架：头部、内容区、卡片区、按钮区、弹层区、列表区、空态区。
2. 从 `HTML` 中继续提取可量化信息：`padding / margin / gap / width / height / font-size / line-height / border-radius / border / shadow` 等，并整理为 UniApp 可落地的尺寸映射；移动端页面优先按 `px -> rpx` 的方式换算，例如 `16px -> 32rpx`、`48px -> 96rpx`、`56px -> 112rpx`。
3. 从设计图中提取视觉信息：颜色层级、图片裁切、图标风格、状态差异与资源表现，用于校验而不是替代 `HTML` 中已有尺寸。
4. 标记可复用区块与状态切换点。
5. 先复用现有 `template/uniapp` 组件、工具、样式变量；找不到合适实现时再新增代码。
6. 对已在 `main.js` 全局注册的通用组件必须直接使用标签，不要在页面内重复 `import` / `components` 注册，也不要重新手写同类结构；当前重点包括：`app-safe-top`、`six-petal-spiral`、`guess-you-like`。

### 第 3 步：把多状态设计图合并到同一页面交互

把同一页面的多张图视作一个页面的不同展示状态，统一在一个 `.vue` 页面中完成，不要拆页规避复杂度。

执行规则：

- 把差异整理为页面状态字段，例如：
  - `activeTab`
  - `loading`
  - `showPopup`
  - `isEmpty`
  - `selectedType`
- 用条件渲染、样式状态类、计算属性、数据驱动视图处理不同状态。
- 对同一区块的多种视觉状态，优先做组件内切换，不要复制整段模板。
- 需要模拟接口数据时，先用静态数据把所有状态搭起来，再根据真实接口改造。

### 第 4 步：创建或更新 UniApp 页面

根据用户给定页面路径直接落盘页面文件。

执行规则：

1. 页面文件放到用户指定路径。
2. 组件结构遵循 UniApp / Vue2 规范：`template` → `script` → `style`。
3. 样式统一使用 `scss`；编写样式前**必须先调用 `uni-css-guard` 技能**，按其固定工作流检查并规避 H5 与微信小程序的 CSS 兼容差异，禁止直接编写未经过跨端兼容审查的样式。
4. 页面主色、按钮色、选中态颜色优先使用全局主题变量，禁止随意硬编码品牌主色。
5. 当用户或项目规范声明页面需统一为“块状圆角风格”时，优先采用“外层浅灰底、内层白色圆角卡片、卡片带柔和阴影”的结构语言；即使设计图局部不是此风格，也要对标题区、表单区、说明区、提示区、弹层区、底部操作容器做统一化卡片处理。
6. 兼容微信小程序，避免使用小程序不支持的动态组件、浏览器专属对象或不兼容语法。
7. 仅实现与当前页面还原直接相关的代码，避免顺手做无关重构。

### 第 5 步：创建或补齐路由

根据目标页面路径，更新 `template/uniapp/pages.json`。

执行规则：

1. 先检查目标路由是否已经存在，存在则复用，不重复新增。
2. 若目标路径属于主包页面，则写入 `pages`。
3. 若目标路径位于已存在分包根目录下，则写入对应 `subPackages`。
4. 若用户给定路径明显位于某个新分包目录，按项目现有结构补充对应分包配置。
5. 默认补齐合理的 `style`，至少包含 `navigationBarTitleText`；若项目当前页面普遍使用自定义导航，则补 `navigationStyle: 'custom'`。
6. 若页面使用 `navigationStyle: 'custom'`，必须使用全局组件 `<app-safe-top />` 处理顶部安全区：H5 不产生额外距离，微信小程序按 `var(--status-bar-height, 0px)` 预留顶部，必要时通过 `mp-extra` 补足胶囊导航区域，并通过 `background` 保持顶部背景连续。禁止在页面内重复手写 `APP-PLUS` 条件占位、独立 `status-bar` 节点或散落的状态栏高度计算；若页面本身顶部已有较大视觉留白，优先调整 `app-safe-top` 的 `mp-extra`，避免安全区与设计稿留白叠加导致首屏整体过低。
7. 必须区分三种“路径表达”：
   - `pages.json` 中主包页面直接写完整 `path`，例如 `pages/index/index`。
   - `pages.json` 中分包页面只在子项里写相对 `path`，例如 `root: 'pages/users'` 下的 `path: 'phoneedit/index'`；但它对应的**完整页面路径**始终是 `pages/users/phoneedit/index`。
   - 页面代码中的跳转路径统一使用带前导斜杠的完整页面路径，例如 `'/pages/users/phoneedit/index'`，不要把分包内的相对 `path` 直接拿去跳转。
8. 对用户汇报“页面路径”或“访问路径”时，默认输出**完整页面路径**，例如 `pages/users/phoneedit/index`，不要只写分包内的 `phoneedit/index`，也不要只写物理文件路径 `template/uniapp/pages/users/phoneedit/index.vue`。
9. 若需要给出当前项目的 H5 本地预览访问地址，必须先检查 `template/uniapp/manifest.json` 中 `h5.router.mode`：
   - 若为 `history`，则按 `http://localhost:8080/<完整页面路径>` 形式表达，例如 `http://localhost:8080/pages/users/phoneedit/index`。
   - 若为 `hash`，则按 `http://localhost:8080/#/<完整页面路径>` 形式表达。
10. 修改完成后，必须再次同时核对：`pages.json` 注册项、页面代码里的 `uni.navigateTo` / `redirectTo` / `reLaunch` 路径，以及对外说明给用户的访问路径，三者是否基于同一个完整页面路径。

### 第 6 步：语法与兼容性检查

页面完成后必须立即自查。

在检查样式之前，**必须先调用 `uni-css-guard` 技能**对当前页面的所有样式进行跨端兼容审查，按其工作流完成高风险写法检索、安全替代、条件编译兜底和模板动态样式检查。

至少执行以下检查：

1. 检查模板语法是否正确，标签闭合、指令写法、条件分支是否成立。
2. 检查 `script` 是否符合 Vue2 / UniApp 写法。
3. 检查样式是否为 `scss`，是否已按 `uni-css-guard` 技能要求完成跨端兼容审查，是否出现明显无效选择器或不兼容写法。
4. 检查是否引入未使用或未定义的变量、组件、方法。
5. 检查是否存在小程序不支持的写法，例如：
   - 运行时动态组件 `<component :is="...">`
   - 未做条件编译保护的 `window` / `document` / `navigator`
   - 仅浏览器可用的 DOM API
6. 若页面使用自定义导航，检查顶部安全区 / 状态栏占位是否真实生效，重点核对 `微信小程序` 首屏是否顶到最上方，同时确认状态栏高度没有与头部原有 `padding-top` 重复叠加，导致内容整体过低。
7. 对已编辑文件运行 lint；若引入新错误，必须先修复再交付。

### 第 7 步：连续三轮 UI 复查（强制量化校验）

> **此步骤为核心质量关卡，不得省略、不得走过场。**
>
> 执行规则：
> - **每轮必须重新读取设计图图片文件和已落盘的 `.vue` 页面代码文件**，禁止凭记忆或上下文残留判断。
> - **每项检查必须明确标注 `PASS` 或 `FAIL`**，附具体证据（CSS 值/行号/像素差），禁止使用"基本匹配""大致一致"等模糊表述。
> - **修复次数限制：每轮最多允许 2 次修复尝试**。流程如下：
>   1. 第 1 次检查 → 有 FAIL → **第 1 次修复** → 重跑当前轮全部检查项
>   2. 第 2 次检查 → 仍有 FAIL → **第 2 次修复** → 重跑当前轮全部检查项
>   3. 第 3 次检查 → 仍有 FAIL → **放弃本轮剩余修复机会，携带已知 FAIL 项进入下一轮审查**（下一轮会再次对这些 FAIL 项进行校验和修复尝试）
> - **三轮全部通过后才允许交付**；若第三轮结束时仍有未解决的 FAIL 项，继续从第一轮重新开始循环（每轮仍享有独立的 2 次修复额度），直到连续三轮全 PASS 或确认某类问题无法在当前条件下解决（此时需明确告知用户具体卡点及原因）。

---

#### 第一轮：布局骨架校验（Layout Skeleton Validation）

**前置动作**：同时打开设计图 `.png` 和当前 `.vue` 文件的 `<template>` 与 `<style>` 区域。

逐项核对并记录：

| # | 检查项 | 校验方法 | 判定标准 | 结果 |
|---|--------|----------|----------|------|
| L1 | 页面顶级容器方向 | 检查根元素 `display` 是 `flex`/`block`/`column` | 设计图是纵向排列则须为 column/flex-direction:column | PASS / FAIL |
| L2 | 区块数量与顺序 | 从上到下列出设计图中的区块名，逐一在 template 中找到对应节点 | 数量完全一致，顺序完全一致 | PASS / FAIL |
| L3 | 单行卡片 vs 多行卡片的布局模式 | 检查含多行内容的卡片是否用了 `flex-direction:column` | 多行内容区块必须是纵向排列，禁止所有子元素挤在一行 | PASS / FAIL |
| L4 | 固定区域定位 | 检查底部栏/导航栏是否使用了正确的定位方式 | 设计图底部固定 → `position:fixed`；顶部固定同理 | PASS / FAIL |
| L5 | 滚动区域边界 | 确认 scroll-view 或可滚动区域的 height 计算是否排除了固定区域 | 内容区不会被固定区域遮挡或产生无法滚动的空白 | PASS / FAIL |
| L6 | 行内元素闭合完整性 | 逐行检查 `<view class="row">` 内部是否有未闭合的子标签或缺少闭合 `</view>` | 每个 row 容器的直接子元素数量与视觉上一致 | PASS / FAIL |

**本轮通过条件：6/6 项均为 PASS。**

#### 第二轮：像素级视觉校验（Pixel-Level Visual Validation）

**前置动作**：提取设计图中可直接量化的 CSS 属性值，与代码中实际值逐条比对。

逐项核对并记录：

| # | 检查项 | 校验方法 | 允许偏差 | 结果 |
|---|--------|----------|----------|------|
| V1 | 页面背景色 | 对比 `background-color` | 完全一致 | PASS / FAIL |
| V2 | 卡片背景色、边框色、圆角值、阴影 | 对比 `.info-card` 等容器样式 | 圆角 ±4rpx 以内，阴影层级需与规范/设计一致 | PASS / FAIL |
| V3 | 卡片内边距 padding | 测量设计图中文字到卡片边缘的距离 | ±8rpx 以内 | PASS / FAIL |
| V4 | 卡片间距 margin-bottom | 测量设计图中两卡片之间的间隙 | ±8rpx 以内 | PASS / FAIL |
| V5 | 标签字号、字重、颜色 | 对比 `font-size`/`font-weight`/`color` | 字号 ±2rpx，颜色完全一致 | PASS / FAIL |
| V6 | 正文/次要文字字号与颜色 | 对比 value/input 的样式 | 字号 ±2rpx | PASS / FAIL |
| V7 | 头像/图标尺寸 | 对应 width/height 值 | ±8rpx 以内 | PASS / FAIL |
| V8 | 按钮高度、背景色、文字色、圆角 | 对比 `.btn` 样式块 | 高度 ±8rpx，颜色完全一致 | PASS / FAIL |
| V9 | 分割线颜色与粗细 | 对比 divider 样式 | 颜色接近，粗细 1-2rpx | PASS / FAIL |
| V10 | 特殊组件样式（如性别切换开关） | 对比选中态/非选态的 background/box-shadow/color | 视觉效果与设计图一致 | PASS / FAIL |

**本轮通过条件：10/10 项均为 PASS。**

#### 第三轮：交互状态与运行态校验（Interaction & Runtime Validation）

**前置动作**：模拟用户操作路径，逐个走通交互流程。

逐项核对并记录：

| # | 检查项 | 校验方法 | 结果 |
|---|--------|----------|------|
| I1 | 导航返回路径 | 追踪 `handleBack` 方法，确认 navigateBack 有 fail 兜底 | PASS / FAIL |
| I2 | 所有 @click 绑定的方法是否都在 methods 中定义 | 全局搜索每个 handler 名 | PASS / FAIL |
| I3 | 表单输入双向绑定 v-model 是否正确指向 data 字段 | 确认 input/select 的 model 变量存在 | PASS / FAIL |
| I4 | 提交按钮的校验逻辑是否完整（必填项、格式） | 检查 handleSave/handleSubmit 中的验证 | PASS / FAIL |
| I5 | 状态切换组件（性别/Tabs/开关）的视觉反馈 | 选中态类名绑定、样式差异是否明显 | PASS / FAIL |
| I6 | 弹窗确认操作（删除/退出）是否有二次确认 | 检查是否调用了 showModal/confirm | PASS / FAIL |
| I7 | API 调用路径是否存在（import 的 api 方法确实导出） | 搜索 api 目录确认方法存在 | PASS / FAIL |

| I9 | 底部安全区兼容（env(safe-area-inset-bottom) + H5 window-bottom） | fixed 底部区域已处理 | PASS / FAIL |
| I10 | 加载状态（v-loading / :loading）是否在异步操作中正确切换 | 检查 loading 状态的 true/false 收敛 | PASS / FAIL |

**本轮通过条件：10/10 项均为 PASS。**

#### 还原度判定与交付标准

**每轮修复机制（每轮独立计算，不跨轮累计）**：

```
第 N 轮 第 1 次检查 → 有 FAIL → [修复 1/2] → 重跑当前轮全部项
第 N 轮 第 2 次检查 → 仍有 FAIL → [修复 2/2] → 重跑当前轮全部项
第 N 轮 第 3 次检查 → 仍有 FAIL → ⚠️ 本轮修复额度用尽，携带 FAIL 项进入下一轮
```

- **三轮全部 PASS**：可以交付，报告总还原度 ≥ 95%。
- **某轮 2 次修复后仍有 FAIL**：停止本轮修复，将剩余 FAIL 项带入下一轮（下一轮重新对这些项检查，享有新的 2 次修复额度）。
- **三轮结束后仍有未解决的 FAIL**：从第一轮重新开始循环审查（每轮重置 2 次修复额度），直到连续三轮全 PASS；若循环 3 次（共 9 轮）后同一 FAIL 项仍无法通过，需明确告知用户该卡点的具体原因及建议的人工介入方案。
- **连续三轮全 PASS 后**，在最终交付说明中附上三张完整的检查结果表（含每项的 PASS/FAIL 判定、修正记录和修复次数统计）。

**禁止行为**：
- 禁止不读取设计图和代码就直接写"OK""匹配""一致"。
- 禁止用模糊描述代替具体 CSS 值对比（如"基本匹配"→ 必须写出"设计图 16px vs 代码 32rpx ✓"）。
- 禁止发现 FAIL 后只口头说"微调一下"但不实际修改代码。
- 禁止三轮检查在同一消息内一次性完成而不做中间修复。

## 输出要求

每次使用此技能，至少交付以下结果：

- 已创建或更新的 UniApp 页面文件。
- 已创建或更新的 `pages.json` 路由项。
- 对多状态设计图的合并实现。
- 已完成语法检查与 lint 自检。
- 简短说明本次完成的页面、路由、状态实现与检查结果。

## 执行约束

执行时遵守以下约束：

- 优先读取真实文件与图片，不凭空猜 UI。
- 优先做最小可行改动，不顺手重构无关代码。
- 页面中若存在多个状态图，必须在一个页面内实现，不拆多个页面糊弄。
- 若项目已有规范组件或样式变量，优先复用。
- 若存在明确的页面风格规范（例如块状圆角卡片风格），优先服从规范；不要因为设计图局部是平面样式就放弃统一的灰底白卡阴影体系。
- 若设计图与 HTML 冲突，以设计图视觉结果为准，以 HTML 结构语义为辅助；但当用户或项目规范明确要求统一视觉语言时，以该规范覆盖设计图的局部偏差。
- **编写任何样式代码前必须先调用 `uni-css-guard` 技能**，按其工作流完成跨端兼容审查后再落代码；禁止绕过该技能直接编写未审查的 CSS/SCSS。
- 修改完成后，必须再次确认页面路径与路由路径一致。
